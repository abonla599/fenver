# 搜索源浏览器直连矩阵（v0.32 W2）

> **这份文档回答一个问题**：用户自带搜索 API key 时，浏览器 / 安卓 WebView 里的前端
> 能不能**不经本站服务器**、直接 POST 源站做搜索。逐源给结论与证据。
>
> 直连成立的前提只有一个：**CORS**。请求形状、鉴权头、判空规则都与后端
> `backend/app/tools/search_api_sources.py`（W1）逐字段同构，由
> `backend/tests/test_web_search_direct_contract.py` 锁住，不怕两边跑偏。

## 矩阵：源 × 是否可直连 × 证据

| 源 | 端点与方法 | 浏览器可直连？ | 证据（2026-10-05 预检，服务器侧 curl 实测） |
| --- | --- | --- | --- |
| 博查 bocha | `POST https://api.bochaai.com/v1/web-search`（Bearer） | **可以**（预检通过，待真机盖戳） | 响应带 `Access-Control-Allow-Origin: *`。预检由需求方在服务端 curl 完成并随 W2 任务单附证据；浏览器内的最终确证走 `probe.html` 第 7 项 |
| Tavily | `POST https://api.tavily.com/search`（Bearer） | **可以**（预检通过，待真机盖戳） | 响应**回显请求 Origin**，且允许 `authorization` 与 `content-type` 头——带 `Content-Type: application/json` + `Authorization` 的 POST 会先发 OPTIONS 预检，这两条正是预检要过的关 |
| Bing（爬取兜底） | 无公开 API，服务端 HTML 爬取 | **不适用** | 它本来就不是"带 key 打 API"的形状：没有 key 可给、浏览器直连会被爬取来源与 CORS 双重挡死。这条源永远只走服务端降级链 |

**"预检通过，待真机盖戳"的诚实口径**：预检证据是服务器侧拿 curl 打的，能证明源站
愿意回 CORS 头；但桌面 Chrome、手机浏览器、安卓 WebView 三者的内核行为并不总一致
（W1 之前模型直连就吃过 WebView 混合内容差异的亏）。所以矩阵里每一行"可以"的**终点**
都是真机跑绿 `probe.html` 第 7 项——步骤见 `docs/真机验证指引.md` 的「搜索源直连」一节。

## 两把 key，各待各的地方

| key | 存在哪 | 谁能配 | 出口 |
| --- | --- | --- | --- |
| **服务端 key**（降级链用） | 本站 `data/search_keys.json`（原子写；POSIX 上 0600，Windows 上权限位不生效、靠 `data\` 的 NTFS ACL 继承） | 管理员，经 `/v1/search-keys`（GET/PUT/DELETE） | 只在服务端出站请求的 `Authorization` 头里；接口响应只有末四位掩码 |
| **本机 key**（直连用） | **这台设备**的 `localStorage`（前缀 `sdkey.`） | 任何人（含未登录访客的设置页） | 只进直连那一发的 `Authorization` 头；**从不发给本站服务器** |

## key 安全红线（逐条对应实现）

1. **key 只留在用户输入的那一侧与出站请求头里**：
   `app.js` 的 `searchDirect()` 是浏览器侧唯一读 `localStorage` 里 key 的函数，key 唯一
   的出现处是 `headers.Authorization`；`probe.html` 第 7 项同理（只活内存，刷新即无）。
2. **绝不进 URL query**：直连只发 POST，端点是固定常量（`index.html` 的
   `data-search-endpoints` / probe 的 `SEARCH_ENDPOINTS`），body 之外不拼任何字符串。
3. **绝不落本站磁盘日志**：直连请求根本不经过本站服务器，天然无日志；服务端 key 一侧
   由 `logsanitizer.register` + audit 只记掩码保证（`search_keys.set_key` 返回的就是掩码）。
4. **绝不出现在任何上报或错误文案**：错误分支一律**不读响应体**（上游可能把请求头原样
   打印回来），只报 HTTP 状态或"请求没能到源站"；`probe.html` 报告沿用「不带 key 片段」
   纪律——连长度与首尾字符都不写。
5. **展示一律末四位掩码**：后端 `mask_key` 口径（≤8 位给 `****`），本机展示
   `sdMask()` 同形。

## 直连不通时的退路（不是失败，是设计）

浏览器直连**永远是加法，不是替换**：

- 本机没配 key、或直连这一发失败 → 聊天里的搜索照旧走服务端降级链
  （博查→Tavily→Bing，`SEARCH_SOURCE_ORDER` 可配），用户无感。
- 服务端连博查/Tavily 的 key 也没配 → 那两家"未启用"（零出站），链子落到 Bing。
- 换句话说：CORS 预检哪天被源站收紧，最坏的损失只是"这一页的直连面板红了"，
  产品的主搜索路径一根毛都不会动。

另一条容易混的路也要说清：v0.37.4 的 `web_read`（读取搜索结果正文）走的是**服务端
出站**（`backend/app/tools/fetch_core.py`），用 `web_search` 签发的短期结果句柄做目的地
准入，**不使用浏览器直连那套 key**。直连面板里配不配 key，都不改变聊天里 `web_read`
的行为；它也不走这段 CORS 矩阵。

## 用量这本账不包含什么（v0.32 W4 补的边界）

v0.32 W4 给服务端降级链加了一本搜索用量账（`core/search_usage.py` → `data/search_usage.json`，
读面 `/v1/admin/search-usage`，管理页「用量 → 搜索用量」那一节）。它只回答三件事：
这个窗口里 `web_search` 真跑了多少次、每次挂在哪个源、每个源的成功率。

**本页面上那套浏览器/WebView 直连的用量不进这本账。** 理由不是嫌麻烦，是物理上看不见：

- 直连那一发是从**用户的设备**直接 POST 到博查/Tavily 的，请求用的是**用户自己的 key**。
  本站既不是它的发起方也不是它的中转方，一个字节都没有经过我们——服务端没有任何一处
  代码能观察到它。要把它记进来，只有一个办法：在设置页每次直连之后回头上报一笔。
- 那条上报路径我们**刻意不建**。它会同时踩坏两样东西：其一，上报的内容是"这个人搜了什么"
  的行为流水，与这本账「没有任何查询原文，也没有哈希」的隐私口径直接冲突；其二，它把
  一本只有服务端可信的账，变成任何人用一条 fetch 就能改写的数——那本账就不再是证据了。
- 所以管理页那一节如实写着：**「用户自带 key 的浏览器/WebView 直连不计：那些请求从用户
  设备直接出站，本站看不见。」** 管理员在那里读到的是"零"，而这个零的含义是
  "本站没跑过"，**不是**"用户没用过"。这两件事必须分得开，宁可少一个数也不造一个数。

同样不进这本账的还有第二类出站请求：**可用性探针**。`tools/availability.py` 每 15 分钟拿
固定的「北京 天气」真跑一次降级链，那是运维检查（判据是"web_search 该不该递给模型"），
不是有人搜了东西。把它记进去等于每小时虚增 4 次搜索。

v0.37.4 的 `web_read` 也不进这本账：这本账只记 `web_search` 真跑降级链的执行；
`web_read` 的成败落在审计（`audit.jsonl` 的 `action=web_read` 行，记
host/path/status/bytes/hops，另加 origin_host/origin_path 与已剥 URL 的 detail），
不写 `data/search_usage.json`。

对照看另一本账的边界：`core/usage.py` 记的是模型调用（谁、多少 token、谁的钱），
搜索用量这本账**没有人这一维**——它按「天 × 源」聚合，同一格里的次数不区分是谁搜的。
v0.37.4 起 `web_search` 确实标了 `needs_user`，但那枚 `user_id` 只用于**结果句柄的归属**
（`[r_...]`）与审计归因，**没有**写进 `data/search_usage.json`：`record_search` 的签名里
就没有"人"这个参数。硬加一列"谁搜的"就是给这本账换一套隐私口径，所以没有加。
