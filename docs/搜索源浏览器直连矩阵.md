# 搜索源浏览器直连矩阵（v0.32 W2）

> **这份文档回答一个问题**：用户自带搜索 API key 时，浏览器 / 安卓 WebView 里的前端
> 能不能**不经本站服务器**、直接 POST 源站做搜索。逐源给结论与证据。
>
> 直连成立的前提只有一个：**CORS**。请求形状、鉴权头、判空规则都与后端
> `backend/app/tools/search_api_sources.py`（W1）逐字段同构，由
> `backend/tests/test_web_search_direct_contract.py` 锁住，不怕两边跑偏。

## 矩阵：源 × 是否可直连 × 证据

| 源 | 端点与方法 | 浏览器可直连？ | 证据（2026-10-05 预检，服务器侧 curl 实测） |
| --- | --- | --- | --- |
| 博查 bocha | `POST https://api.bochaai.com/v1/web-search`（Bearer） | **可以**（预检通过，待真机盖戳） | 响应带 `Access-Control-Allow-Origin: *`。预检由需求方在服务端 curl 完成并随 W2 任务单附证据；浏览器内的最终确证走 `probe.html` 第 7 项 |
| Tavily | `POST https://api.tavily.com/search`（Bearer） | **可以**（预检通过，待真机盖戳） | 响应**回显请求 Origin**，且允许 `authorization` 与 `content-type` 头——带 `Content-Type: application/json` + `Authorization` 的 POST 会先发 OPTIONS 预检，这两条正是预检要过的关 |
| Bing（爬取兜底） | 无公开 API，服务端 HTML 爬取 | **不适用** | 它本来就不是"带 key 打 API"的形状：没有 key 可给、浏览器直连会被爬取来源与 CORS 双重挡死。这条源永远只走服务端降级链 |

**"预检通过，待真机盖戳"的诚实口径**：预检证据是服务器侧拿 curl 打的，能证明源站
愿意回 CORS 头；但桌面 Chrome、手机浏览器、安卓 WebView 三者的内核行为并不总一致
（W1 之前模型直连就吃过 WebView 混合内容差异的亏）。所以矩阵里每一行"可以"的**终点**
都是真机跑绿 `probe.html` 第 7 项——步骤见 `docs/真机验证指引.md` 的「搜索源直连」一节。

## 两把 key，各待各的地方

| key | 存在哪 | 谁能配 | 出口 |
| --- | --- | --- | --- |
| **服务端 key**（降级链用） | 本站 `data/search_keys.json`（0600，原子写） | 管理员，经 `/v1/search-keys`（GET/PUT/DELETE） | 只在服务端出站请求的 `Authorization` 头里；接口响应只有末四位掩码 |
| **本机 key**（直连用） | **这台设备**的 `localStorage`（前缀 `sdkey.`） | 任何人（含未登录访客的设置页） | 只进直连那一发的 `Authorization` 头；**从不发给本站服务器** |

## key 安全红线（逐条对应实现）

1. **key 只留在用户输入的那一侧与出站请求头里**：
   `app.js` 的 `searchDirect()` 是浏览器侧唯一读 `localStorage` 里 key 的函数，key 唯一
   的出现处是 `headers.Authorization`；`probe.html` 第 7 项同理（只活内存，刷新即无）。
2. **绝不进 URL query**：直连只发 POST，端点是固定常量（`index.html` 的
   `data-search-endpoints` / probe 的 `SEARCH_ENDPOINTS`），body 之外不拼任何字符串。
3. **绝不落本站磁盘日志**：直连请求根本不经过本站服务器，天然无日志；服务端 key 一侧
   由 `logsanitizer.register` + audit 只记掩码保证（`search_keys.set_key` 返回的就是掩码）。
4. **绝不出现在任何上报或错误文案**：错误分支一律**不读响应体**（上游可能把请求头原样
   打印回来），只报 HTTP 状态或"请求没能到源站"；`probe.html` 报告沿用「不带 key 片段」
   纪律——连长度与首尾字符都不写。
5. **展示一律末四位掩码**：后端 `mask_key` 口径（≤8 位给 `****`），本机展示
   `sdMask()` 同形。

## 直连不通时的退路（不是失败，是设计）

浏览器直连**永远是加法，不是替换**：

- 本机没配 key、或直连这一发失败 → 聊天里的搜索照旧走服务端降级链
  （博查→Tavily→Bing，`SEARCH_SOURCE_ORDER` 可配），用户无感。
- 服务端连博查/Tavily 的 key 也没配 → 那两家"未启用"（零出站），链子落到 Bing。
- 换句话说：CORS 预检哪天被源站收紧，最坏的损失只是"这一页的直连面板红了"，
  产品的主搜索路径一根毛都不会动。
