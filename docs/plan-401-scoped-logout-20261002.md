# Plan: Make a single 401 expire only the current identity (and tell users to re-login, not re-register) so that one stale token never wipes the whole device's accounts, model bindings, and session pointers.

**Complexity:** Small — 4 edit sites in 2 known files + 1 contract test; no new interfaces.

## Goal

Enable a logged-in user whose *one* token has been evicted/expired to re-login and keep every other local account, model binding, and session pointer intact, so that a 401 no longer looks like "model lost + sessions lost".

## Background (root-cause chain, from sde-debug)

1. Server design: `MAX_SESSION_TOKENS = 8` per account silently FIFO-evicts the oldest token on each new login (auth.py:43, 327-332). Frequent logins across phone + web today legitimately produced 401s.
2. Shell defect (the real bug): any 401 anywhere triggers `Prefs.clearAuth()`, which wipes **all** local identities — tokens, `providerId` (= "模型丢失"), `lastSessionId` (= "会话丢失"). Sites: `ChatUi.kt` `logoutIf401()` (line ~238) and `SessionListUi.kt` 401 branch (line ~84).
3. Misleading copy: "未登录或令牌已失效：请在「设置 → 账户」重新注册" (native `SettingsUi.kt:916` + web `app.js` `memoryListErrorText`) steers users to *register a new account*, making old-account sessions appear permanently lost. Server data is intact.

Refuted hypotheses: server data dir moved; APK signing drift (CI apksigner fingerprints identical since v0.23.17); backend auth regression between v0.25→v0.28 (no auth code diff); corrupt APK install (Updater verifies SHA-256 and rejects 3xx).

## Deliverables

- Kotlin fix: `ChatUi.kt logoutIf401` uses `Prefs.forgetCurrent()` instead of `Prefs.clearAuth()` → only the failed identity is dropped; other accounts survive.
- Kotlin fix: `SessionListUi.kt` 401 branch switched the same way.
- Copy fix (kept verbatim parity across both surfaces): "重新注册" → "重新登录" in native `SettingsUi.kt` and web `app.js memoryListErrorText`.
- Backend contract test (house grep-style pytest): pins that no `clearAuth()` call remains on any 401 path in the two shell files and that both copy surfaces say "重新登录", never the old "重新注册" phrase on the 401 line.

Out of scope: changing `MAX_SESSION_TOKENS` (server design decision — surfaced to user as a follow-up recommendation, not changed here).

## Acceptance Criteria

- AC-1 [Happy] Given a device with N>1 identities, when one request returns 401, then only that identity is forgotten locally and the remaining N-1 entries keep token/providerId/lastSessionId.
- AC-2 [Error path] Given the evicted identity is the current one, the shell still routes to the login screen (behavior of `onLoggedOut()` unchanged).
- AC-3 [Edge] The 401 error copy on both web and native tells the user to 重新登录 (re-login), and does not contain the "重新注册" phrase on that line; both texts remain byte-identical to each other.
- AC-4 [Regression guard] New pytest contract test fails against pre-fix source and passes post-fix; existing backend tests unaffected.
