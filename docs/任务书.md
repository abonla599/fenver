## 1. 最终目标

### 1.1 一句话

**一个用户手机和浏览器上都在线、有自己风格的私人助理：它能看见、能记住、能查、能规划，
在真正需要动手的地方停在「等人按最后一下」的位置。**

### 1.2 拆成可验收的五句话

1.0 交付的不是「全自动」，是这个：

| 能力 | 1.0 交付形态 | 硬边界 |
|---|---|---|
| 对话与记忆 | ✅ 自动：多轮、跨会话、长期记忆可检索 | 无 |
| 查资料 | ✅ 自动：搜、读、抓正文、给出来源 | 无 |
| 看现在状态 | ✅ 自动：能回答「我手机上现在是什么」「今天的安排」 | 只读，不点不看密码 |
| 复杂任务 | ✅ 自动到**关键一步之前**，把人叫来确认 | 见 §2 |
| 动手操作 | ⚠️ 收到「支付页已打开」「提交订单页已填好」就停 | 支付永不自作主张 |
| 多设备 | ⚠️ 电脑干活，手机当审批器 | 不做跨设备越权 |

### 1.3 什么叫「有自己风格」

不是皮肤，是三条具体的东西：

- **一个号码**：同一处永远只显示一个版本号，不做「通道说 A、装的是 B」这种并排摆。
- **说人话**：失败文案给「怎么办」，不给堆栈；能自动的就别让用户按按钮。
- **不留谎话**：界面承诺的机制必须有判据钉在代码上，做不到的事写进 README 而不是藏起来。

## 2. 硬边界（写死防漂移）

这一节是**否决清单**。历史上每次想「先做出来再说」，最后都是返工。

### 2.1 永远不做

| 不做 | 为什么（不是技术问题） |
|---|---|
| ❌ 自动支付 / 转账 / 代绑卡 | 出事平台担责、用户担责、产品担责。用户要自己按那一下指纹。 |
| ❌ 绕过验证码 / 绕过风控 | 用户的号比 agent 的功能值钱。 |
| ❌ iOS 自动化 | Apple 不开放任何第三方自动化接口，这不是能攻的墙。 |
| ❌ 冒充本人在聊天软件发消息 | 身份冒用，责任无法界定的灰色地带。 |
| ❌ 代做金融决策 | 投顾牌照问题，不是产品问题。 |
| ❌ 抓取需登录且平台明确禁止的内容 | 同上。 |

### 2.2 架构层面不做

| 不做 | 理由 |
|---|---|
| ❌ 桌面形态（agent 控制这台 Windows） | 产品战略是**在线多租户**。服务端看到的是这台机器的屏幕，不是用户的电脑——那不是产品能力，是架构错位。要 PC 能力就另立独立受控代理，单独立项，不占 1.0 关键路径。 |
| ❌ 后台持续录屏 / 常驻采集 | 隐私、耗电、审核风险都高一个量级。一律**按需快照**。 |
| ❌ 基于坐标的点击 | 主流 App 改版一次就失效，是维护成本黑洞，不是功能缺陷。 |

### 2.3 为什么这些边界要写进文档而不是记在脑子里

因为它们**每次都会被重新提出来**，而且提的时候都很有道理（「用户就要这个」「竞品都有」）。
写在这里，下一个接手的人才有东西可以指着说「这条 2026-10 就判过了」。

### 3.2 两条 tag 线是**故意分开**的，不要合并

```
服务端线：v0.40.1  ← 每周左右一版，只换后端包
安卓线：  v0.36.9  ← 每月左右一版，只在装 APK 时变
```

理由（2026-10-23 拍板，有事故背书）：两线共用一号时，服务端发版会让手机端「检查更新」
报出一个**装不上**的版本号——v0.34.2 那次真实发生过。分开之后，设置页只显示已经装上的
那个号，通道只宣告能下载的那一版。

判据在 `backend/tests/test_v0342_single_version_row_contract.py` 与 changelog 的两把锁里。

### 3.4 计划与实际偏离的实证（读 §4 前必看）

| 提案里的号 | 提案主题 | 实际发了什么 |
|---|---|---|
| v0.37 | PC 感知 | 安全与日志治理 |
| v0.38 | PC 动作 | 官网产品化改版（site-only） |
| v0.39 | 移动端感知 | 模型驾驶舱（网页版 UI） |
| v0.40 | 移动端动作 | 下载提速 + 上下文自动压缩 |

**这不是失控，是优先级重排**：用户在真机上提的每一条（语音收不到声音、四角有缝隙、
下载太慢、会话要加载一下）都比「按计划推下一个大版本」更要紧。但结论是硬的——
**别拿计划表推断「现在该做哪一版」**。

### 3.5 已知的、反复踩的坑（写下来省下一个人三轮）

1. **这台仓库目录就是生产机。** `dist/run_backend/` 里跑的就是 `https://ai.fenever.xyz`。
   在进程内 `import app.main` 跑一次**不是沙箱**，是真的在动线上数据。
   任何验证脚本的第一行职责是**把数据路径指走并自证**（`PROVIDERS_DB_PATH` / `DATA_ROOT` /
   `SESSION_DB_PATH` / `AUDIT_LOG_PATH`），第二行才是验证业务逻辑。
   2026-11-26 我没做到，改坏了生产 `data/providers.json`（已用备份还原）。
2. **`Start-Process` 不带输出重定向会挂住父进程。** 已在 `watchdog.ps1` 与 `swap-package.ps1`
   各补两处；11-13 与 11-27 两次事故都是它。新加拉起后端的代码，一律带
   `-RedirectStandardOutput/-Error`。
3. **`swap-package.ps1` 必须保持纯 ASCII 无 BOM**（PS 5.1 会把非 ASCII 字节错解码成语法错误）。
   注释写英文，锁会当场抓。
4. **编辑 CRLF 文件后再统一回原行尾。** 否则 `git diff` 从几十行炸成几千行，审查时看不见真改动。
   已踩五次。
5. **某些开发机（含这台生产机）的 Python 进程写不了系统临时目录**：沙箱按 workspace
   边界放行，不是 ACL 问题，改 ACL 没用），`tempfile.gettempdir()` 回落到仓库根，撞
   `_prod_data_guard` 的 fail-closed。**所以 CI 是唯一可信的测试判据。**

## 4. 阶段大纲

五个阶段。**每段有明确的退出条件**，没到就不要开下一段——历史上的返工都发生在「上段的
验收判据还没跑通就开始铺下段」。

```
          ┌─────────────────────────────────────────────┐
          │  P0 稳定（现在在这里）                        │
          │  线上不出事 / 发版能走完 / 债还清            │
          └──────────────────┬──────────────────────────┘
                             ↓ 退出：连续 3 次发版零事故
          ┌──────────────────┴──────────────────────────┐
          │  P1 看得见（只读感知）                        │
          │  手机屏幕 / 通知 / 剪贴板，一个像素都不点     │
          └──────────────────┬──────────────────────────┘
                             ↓ 退出：真机 5 条验收全过
          ┌──────────────────┴──────────────────────────┐
          │  P2 记得住、办得成（任务可挂起 + 技能库）     │
          │  长任务能中途问人，同一任务两次结果一致       │
          └──────────────────┬──────────────────────────┘
                             ↓ 退出：技能跑 5 次步骤序列一致
          ┌──────────────────┴──────────────────────────┐
          │  P3 能动手（动作，支付卡死不做）              │
          │  到支付页/提交页就停，等人按最后一下          │
          └──────────────────┬──────────────────────────┘
                             ↓ 退出：真机完成一次真实下单到支付页
          ┌──────────────────┴──────────────────────────┐
          │  P4 收敛（1.0）                              │
          │  双端矩阵 / 审计复跑 / 文档换骨 / 开源叙事    │
          └─────────────────────────────────────────────┘
```

### 4.1 为什么是这个顺序

| 顺序 | 依赖关系 |
|---|---|
| P0 先 | 地基不稳的时候做功能，等于在漏水的船上装发动机。**P0 的退出条件不是「债还完了」，是「连续 3 次发版零事故」**——债永远还不完。 |
| P1 在 P2 前 | 任务要能挂起问人，前提是它有东西可问。「看得见」是「办得成」的输入。 |
| P2 在 P3 前 | 没有技能库就做动作，等于每次现编一套点击序列，改版一次全废。**技能是动作的载体**。 |
| P3 在 P4 前 | 动手能力是 1.0 的卖点也是最大风险，必须留出发版后观察期。 |

### 4.2 每段的规模预期

**不要拿「两周一版」排这些阶段。** 历史 v0.23→v0.30 是两周八版，但那八版都是加一个工具、
改一层 UI。P1 之后每一段都涉及 OS 级权限或不可逆的外部动作。

| 阶段 | 规模 | 说明 |
|---|---|---|
| P0 | 3–5 个小版本 | 单项都不大，但数量多、每项都要配锁 |
| P1 | 3 个小版本（可并行三轨） | Android / 服务端 / 安全三条轨道，见 §5.2 |
| P2 | 3–4 个小版本 | 任务状态机 + 技能库，是最大的一块 |
| P3 | 3 个小版本 | 风险最高，建议 4 周以上一版 |
| P4 | 1–2 个版本 | 主要是复跑与重写文档 |

| 临时目录污染版本库 | 已加 4 条 `.gitignore` 规则；**根因是我的验证脚本习惯在仓库内建临时树**，规则只是兜底 |

### 5.2 P1 看得见 —— 只读感知

**目标**：让 agent 能回答「我手机上现在是什么」，并把这幅画面用进对话。**一个像素都不点。**

**为什么现在可以做**：服务端那半边**已经在仓库里**（`core/device_context.py` + `core/device_context_router.py`
+ `tools/device_context_tool.py` + `core/tests/test_v040_device_context.py`），安卓侧只落了
**数据形状**（`core/DeviceContextPayload.java`：本地脱敏、上限、wire JSON）。
缺的是**采集端**——`AccessibilityService`、权限向导、前台服务、状态条。

> ⚠️ 所以 P1 的工程量主要在 Android，不在服务端。**服务端那半边请先读一遍再决定改不改**，
> 别重复实现已经存在的东西。

#### P1.1 三条并行轨道

| 轨道 | 内容 | 能否并行 |
|---|---|---|
| A Android | AccessibilityService、权限向导、前台服务、状态条、按需快照 | 与 B 并行，**前提是 wire schema 先冻结** |
| B 服务端 | 复核 `/v1/device/context`、TTL、`device_context` 工具可见性 | 与 A 并行，旧 APK 兼容 |
| C 安全 | 威胁模型、脱敏规则、注入防护、变异测试 | 与 A/B 并行，只读 + 测试 |
| D 发布 | versionName/versionCode、APK、更新通道、真机矩阵 | **等 A/B/C 合流，串行** |

**不能并行**：同一棵 Android 树上的安全收尾与 P1；发版链；push/tag/换包/workflow 改动。

#### P1.2 小版本切分

| 小版本 | 主题 | 内容 |
|---|---|---|
| A1 | 节点树 + 权限引导 | AccessibilityService、权限向导、按需快照、真机拒绝/授权路径 |
| A2 | 通知 / 剪贴板 | 通知栏读取、剪贴板前台读取、独立 opt-in、降级路径 |
| A3 | 截图 / 视觉 | MediaProjection 按次授权、用户预览、压缩尺寸上限、视觉 provider 链路 |

#### P1.3 验收判据（七条，逐条可验）

1. 模型能回答「我手机上现在打开了什么 app」；未授权时工具 `available()` 为 `False`，模型看不到
2. 权限引导页说清范围；拒绝后功能降级不崩
3. 截图/节点内容**不落盘、不进日志**（契约测试扫文件与日志）
4. 密码字段永不序列化；支付/验证码类字段本地脱敏
5. 单次负载 ≤128KB、节点 ≤400、深度 ≤30（常量已在 `core/device_context.py:29-31`）；TTL 到期即不可读
6. **本版不存在任何点击/输入注入代码**（AST 扫描钉死）
7. 变异锁：删密码脱敏、删权限 gate、删 TTL，三条都必须红

#### P1.4 设计要点（别重新发明）

- **按需快照，不做持续采集**：隐私、耗电、审核风险都低一个量级
- **文本优先，截图最后**：节点树比 OCR 稳、便宜、可脱敏
- **本地脱敏再上传**：密码、验证码、卡号、身份证在设备侧就删，服务端只做第二道
- **复用现有审批/挂起**：不造新 SSE 帧，不改客户端事件契约
- **能力级开关**：`device_context_enabled` + 每用户/每设备撤销 + 远程 kill switch
- **旧客户端兼容**：新端点/新工具纯增；旧 APK 不看、不传、不受影响
- **可观测但不看内容**：只记次数、延迟、负载大小、失败原因；不记屏幕文本
- **设备上下文是不可信数据**：包在 `<device_context untrusted>` 里，禁止当指令；控制字符清洗

### 5.3 P2 记得住、办得成

**目标**：长任务能中途问人并从断点继续；同一件事跑两次结果一致。

**退出条件**：某个技能的步骤序列跑 5 次完全一致；进程重启后挂起的任务能续上。

#### P2.1 任务可挂起（地基，必须先做）

现状核实（2026-11-28）：`TaskStatus` 已是 `waiting_user` 那套（v0.35 A1 落地），
审批票据落盘也做了。**要先读 `backend/app/agents/task_store.py` 与 `core/approval.py` 确认**，
别按旧提案里「5 态、`_tickets` 内存」写——那两句已经过期了（旧提案自己的更正段就记着这事）。

| 任务 | 判据 |
|---|---|
| 工具执行协议支持「挂起 → 等外部输入 → 恢复」 | 跑到第 3 步需要验证码的任务能挂起 5 分钟，用户输入后从第 4 步继续，全上下文不丢 |
| 审批票据 TTL 可配置（长任务需 5–10 分钟） | 3 分钟任务第二次确认时票据仍有效 |
| 用户不响应 ≠ 失败 | 超时进入 `needs_input` 挂起保活，不是整轮失败 |
| 后端重启后挂起任务可续 | 重启进程，挂起任务列表还在，点继续能跑 |

#### P2.2 技能与场景库

**从「demo 能跑」到「产品能用」的关键一版。** 全靠模型每次现规划的话，同一任务跑两次结果
可能不同——那不叫产品。

| 任务 | 判据 |
|---|---|
| 技能 = 前置条件 + 参数 + 步骤 + 检查点 + 失败处理，可增删改查 | 建一个技能、改一个参数、再跑 |
| 内置首批：比价、点外卖、订酒店、资讯简报 | 四个都能跑通（P3 之前只到「给建议」） |
| 技能可被用户改（「我点外卖永远不要辣」） | 改一个参数，后续所有执行都用新参数 |
| 执行时逐步显示进度（复用 credits 消耗显示） | 界面上能看到第几步 |
| 失败从检查点恢复 | 中途失败续跑不从头 |

#### P2.3 记忆质量（与 P2.1 并行）

这一块交接文档里没编号，但它是「记得住」的另一半：

- 记忆检索的相关性（现在只有嵌入召回，没有重排）
- 记忆的时效（旧事实 vs 新事实冲突时怎么办）
- 用户可查、可删、可改（现在只能看条数）

### 5.4 P3 能动手 —— 动作，但支付卡死

**目标**：完成「到支付页/提交页就停，等人按最后一下」。

**这是全项目风险最高的一段。** 不可逆的外部动作 + OS 级输入注入，两者叠加。

#### P3.1 先决条件（不满足就不要开工）

1. P1 的真机验收七条全过（看得见才谈得上点得准）
2. P2 的技能库能稳定复现同一序列（否则每次现编点击序列，改版一次全废）
3. §2.1 的六条否决清单在代码里有常量 + README 双落点

#### P3.2 任务

| 任务 | 判据 |
|---|---|
| 输入注入（点击/滑动/输入）走 AccessibilityService，不走向标坐标 | 主流 App 小改版后仍能用 |
| **支付边界硬编码**：识别到支付/验证码/银行页面立即停下并呼叫用户 | 变异锁：删掉这条判断 → 测试红 |
| 每步可回滚、可中断、有超时 | 中途停止不会留下半完成状态 |
| 动作前的二次确认（复用 P2 的审批卡） | 每个不可逆动作前都有人确认 |
| 风控友好：限速、随机化、不并发 | 不做反爬对抗，但也不主动触发风控 |

#### P3.3 验收判据

1. 真机完成一次真实下单到**支付页已打开**，最后一步由用户完成
2. 识别到验证码页面时停下并呼叫用户，不尝试绕过
3. 本版所有动作代码里，**没有一条**能自动完成支付（AST + 文案双扫描）
4. 变异锁：把「支付页停下」改成「继续」→ 三条测试同时红

## 6. 工作纪律（每一条都有事故背书）

### 6.1 发版顺序是机器把关的，不许凭记忆

```
CI 全绿 → 本地全量复跑 → 打本地 tag → pre_tag_gate --pre-build
  → 构建 staging → 换包 → 线上验收 → pre_tag_gate → 推 tag → Release → 播报
```

**跳过 `pre_tag_gate` 就是它在拦的那两次事故的复现。** 它现在有七关，其中第 7 关
（上一版内容还在不在，#291）是 2026-11-26 才加的——那次官网内容丢了，闸门全程绿，
就是因为没有这一关。

### 6.2 改了发版说明必须同笔重算 changelog

```bash
venv\Scripts\python.exe tools\gen_changelog.py
```
漏了会让 changelog 锁在 CI 变红，看起来像产品坏了。

### 6.3 破坏性操作串行 + 留台账

删文件/目录、`git worktree remove`、`git branch -D`、换包、打 tag、推 main、改 workflow——
同一时刻只许一个人做。动手前读 `docs-internal/本机清理台账.md` 最后几条；不可再生的内容
先取证；执行后台账追加一条（动了什么 / 依据哪句授权 / 可恢复指针 / 回滚方法）。

### 6.4 运行期资产永不清理

`data/`、`chroma_db/`、`venv/`、`version.txt`、`dist/`、`.env`。
**`chroma_db` 里有真实记忆，重建即丢失。** chromadb 的 CVE 等上游修，绝不重建向量库。

### 6.5 写注释前先实跑一遍

2026-11-13 交接文档记着：「那 5 处假话里有 2 处是专门去改假话的批自己新写出来的」。
禁会腐烂的数（「5 次」「209→301」这类）；写机制说明前先验一次。

### 6.6 需要用户单独授权才能做的动作

| 动作 | 说明 |
|---|---|
| 后端换包 | 会停服几十秒，用户能感知 |
| 推 main / 合并 main | 快进可以，强制改写历史要单独说 |
| 对外播报 / 发公告 | 措辞与渠道需用户定 |
| 删远端 tag / 删 Release | 属对外撤回 |
| 清理临时工作树与已并入分支 | 破坏性串行 |
| 思考 profile 的 live 出网调用 | 花配额 |
| 任何 §2 边界内的能力 | 先改本文，再动代码 |
